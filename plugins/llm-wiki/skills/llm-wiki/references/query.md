# query — Wiki検索・統合回答

`query <質問>` は Wiki 内の関連ページを横断的に検索し、統合した回答を返す。新切り口が出た場合は新ページの提案・作成も行う。

## 検索アプローチ

設計思想は [SKILL.md](../SKILL.md) の「検索の方針」を参照。本ドキュメントでは具体的な実行手順を示す。

実行ステップ:

1. **ジャンル特定** — root index でジャンル候補を絞る
2. **ジャンル内コンテキスト把握** — `_overview.md` と `index.md` を読んで候補ページを選定
3. **ページ Read + wikilink 拡張** — 選定ページと関連ページを読む
4. **Grep フォールバック** — 1〜3 で情報不足の場合のみ、追加 Read
5. **統合回答の生成** — 集めた情報をまとめる
6. **保存判断** — 新ページ化するか判断
7. **完了レポート**

### Read 上限（コンテキスト爆発防止のハードリミット）

- **候補ページの Read 上限: 合計 8 ページ**（ステップ2 で初期選定 5、ステップ3/4 で追加 3）
- **メタファイルの Read（`index.md` / `_overview.md`）はこの上限に含めない**（別枠）
- ステップ1.5（全ジャンル横断）の Read もメタ枠（候補ジャンル数に応じる）

### 並列 Read の原則（往復削減）

Read は **依存レベルごとにまとめて 1 メッセージ内で並列発行**する。1 ファイルずつ逐次に読まない。逐次に読むと往復回数・レイテンシ・毎ターン再カウントされる cache_read が膨らむ。読むファイル集合は同じまま往復だけを畳むので、回答品質は不変。

依存があるのは**レベル間だけ（root → ジャンル → ページ → wikilink の各 hop）**。同一レベル内の Read は必ず束ねる。

- **レベル1（必ず単独）**: root `index.md` — どのジャンルかを決めるため最初に単独 Read（ステップ1）
- **レベル2（並列）**: 候補ジャンルが確定したら、全候補ジャンルの `_overview.md` と `index.md`、および `type: synthesis` 判定用の `Grep -l` を **1 メッセージにまとめて発行**（ステップ2）。`Grep -l` は Read ではなく、従来も必要だった候補ページ識別を同じ依存レベルに前倒しするだけ。Read するファイル集合は変えない
- **レベル3（並列）**: 候補ページが確定したら、選定した全ページを **1 メッセージで並列 Read**（ステップ3）
- **レベル4以降（hop ごとに並列）**: wikilink 拡張は **hop ごとに 1 つの依存レベル**。同じ hop で追う複数ページは 1 メッセージで並列 Read し、次の hop は前 hop の内容を読んでから（＝別レベル）。最大 2hop まで（ステップ3）

## ステップ1: ジャンル特定

- `$WIKI_ROOT/index.md` を Read（必ず最初に実行）
  - root index にはジャンル一覧が並ぶ。各行に 1 行サマリが付いていれば判断材料に使う
  - サマリ未整備の既存 vault ではジャンル名から推測する
- 質問内容と各ジャンルを照合し、関連ジャンル候補を 1〜3 個に絞る
- 候補ジャンルが特定できない場合 → ステップ1.5 へ

### ステップ1.5: 全ジャンル横断（候補不明時のみ）

ステップ1 でジャンルを絞れない、または質問が複数ジャンルにまたがる可能性がある場合に実行する。コンテキスト爆発を防ぐため次のガードを適用する:

- **ジャンル数 5 個以下**: 全ジャンルの `_overview.md` を `Glob "$WIKI_ROOT/wiki/*/_overview.md"` で取得し、**1 メッセージ内で並列 Read**（1 ファイルずつ逐次に読まない）。各 Read は冒頭〜「## 知識マップ」見出しまで（先頭 30 行程度）に留める
- **ジャンル数 6 個以上**: 全 Read は避ける。root index のサマリ（既にステップ1で読み込み済み）を再評価し、ジャンル名から関連性を推測。それでも候補が浮上しない場合のみ、特に関連が疑われる 2〜3 ジャンルに絞って `_overview.md` を **並列 Read**
- いずれの場合も候補が浮上しないなら → ステップ4（Grep フォールバック）へ

## ステップ2: ジャンル内コンテキスト把握

候補ジャンルの**メタファイルと synthesis 判定を 1 メッセージ内で並列発行**する（[並列 Read の原則](#並列-read-の原則往復削減) のレベル2）。候補が複数ジャンルなら全ジャンル分を同じメッセージにまとめる。逐次に 1 ファイルずつ読まない。同一メッセージに含めるもの:

- 各候補ジャンルの `$WIKI_ROOT/wiki/<genre>/_overview.md` の Read
- 各候補ジャンルの `$WIKI_ROOT/wiki/<genre>/index.md` の Read
- 各候補ジャンルの `Grep -l "type: synthesis" "$WIKI_ROOT/wiki/<genre>/"*.md`（synthesis ページ識別用。index.md カタログには `type` が無いため）

結果が揃ったら読み取る:

- `_overview.md`: 「## 知識マップ」のツリーから質問が当たるノードを特定。「## 横断テーマ」に質問関連の論点があれば注目（横断統合型の質問では最重要）
- `index.md`: 「## ページ一覧」のカテゴリ別カタログから候補ページを選定。1行サマリを手がかりに、ページ本文を読まずにここで取捨選択

このステップで選定する候補ページ数の上限は **5 ページ**（複数ジャンル横断時もこの上限内）。`_overview.md` / `index.md` / synthesis 判定 Grep はこの 5 ページにカウントしない（メタ Read のため別枠）。

候補ページの優先順位:

1. `type: synthesis` ページ（横断知識の集約点）。比較・全体像の質問では真っ先に当たる
2. `_overview.md` の「## 横断テーマ」で言及されているページ
3. その他カタログから選んだ候補

## ステップ3: ページ Read + wikilink 拡張

- ステップ2で選定したページを **1 メッセージ内で並列 Read**（レベル3。逐次に 1 ページずつ読まない）
- 各ページの `## 関連ページ` セクション・本文中の `[[wikilink]]` から関連が強いものを判断
- 追加で辿るページは **hop ごとに 1 メッセージで並列 Read**（同じ hop の複数ページは必ずまとめて発行。次の hop は前 hop を読んでから）

hop の数え方: ステップ2で選定したページを 0hop、そこから wikilink で 1 段辿ったものを 1hop、さらに辿ったものを 2hop と数える。最大 2hop まで。

ページ数の上限: ステップ3 と ステップ4 を合算した追加 Read は **3 ページ** まで（ステップ2 と合わせて候補ページ合計 8 ページ上限）。

例（追加 Read 3 枠を使い切るパターン）: 1hop 目で 2 ページ Read、2hop 目で 1 ページ Read → 追加 Read 上限 3 に到達。

リンクされていても主題から外れるページは追跡しない。

## ステップ4: Grep フォールバック（条件付きで実行）

ステップ1〜3 で集めた情報を見て、ステップ5（統合回答生成）に進む前に充足判定する。次のいずれかに該当する場合のみ Grep フォールバックを実行する。該当しなければスキップしてステップ5 へ進む。

発火条件:

- (a) ステップ1.5 でも該当ジャンルが特定できなかった
- (b) ステップ2で候補ジャンルの `index.md` / `_overview.md` に質問関連の見出し・ページが一切ない
- (c) ステップ3でページを Read したが情報が決定的に不足している（Wiki に該当知識がほぼ無いことを意味する）

実行手順:

- スコープを可能な限り絞る:
  - ジャンル候補があれば `Glob "$WIKI_ROOT/wiki/<genre>/*.md"`
  - 全く絞れなければ `Glob "$WIKI_ROOT/wiki/*/*.md"`
- 質問のキーワードを複数バリエーション（同義語・略語・大小文字）で `Grep` する
  - 例: 「インデックス」「index」「INDEX」「B木」「BTree」
- ヒットしたページは ステップ3 と同じ要領で Read（合計上限・hop ルールも同じ。すでに使った追加 Read 枠から差し引く）
- フォールバックを使った旨と理由を ステップ7 の完了レポートに記録する

## ステップ5: 統合回答の生成

- 関連ページの内容を読み、質問に対する統合回答をまとめる
- **引用は3階層で示す**（読み手が検証経路を辿れるようにする）:
  1. **Wikiページ**: `[[ページ名]]` を **主張ごとにインライン引用** する。冒頭まとめだけで済ませない。具体的な事実・数値・人名・年代を述べる文には必ず由来 wikilink を添える
  2. **ソースページ（raw 原文）**: 個別の事実・引用文・統計値を述べる際は、その出典ソースを `[[sources/<genre>/<file>]]` で併記する（Wikiページの frontmatter `sources:` から引く）。`type: source` のソースは raw 原文を保持しているため、**正確な引用・実装サンプル・原典の詳細が必要なときはこのソース本文を直接 Read** すればよい（情報が欠落しない）。ただし旧 `type: source-summary` のソースは本文が要約で原文が欠落している場合があるため、逐語引用や実装サンプルの根拠には使わず、`source_url:` の外部 URL を辿って一次情報を確認する
  3. **外部URL**: ソースページの frontmatter に `source_url:` がある場合、または本文中に外部リンクがある場合は、特に「最新性が問われる事実」「論文・公式発表・著者名つき発言」では括弧書きで URL を併記する
- インライン引用の例: 「Werner Vogels が AWS re:Invent 2025 で提起 ([[検証負債]] / [[sources/software-engineering/コードレビューとは何か]])」
- 矛盾する記述があれば「ページA は X と書く一方、ページB は Y と書いている」と並べる（勝手に統合しない）
- ページに無い情報を自分の知識で補う場合は「Wikiには記述なし」と明示する
- 冒頭または末尾に「**参照Wikiページ**」「**参照ソース**」のリストを付け、本文で言及した全リンクを再掲する（読み手が一目で参照範囲を把握できるようにする）

## ステップ6: 保存判断

[decision-rules.md](decision-rules.md) の「query結果を保存する/しない」基準に従って判断する。

### 保存すべきケース

- 既存ページに無い新切り口・視点が出た
- 新コンセプトが導入された
- 再利用性が高い汎用的な分析・比較
- 複数ソース由来の知識を統合する横断的洞察

このときはユーザーに「この回答を新規ページとして保存しますか？」と確認し、合意があれば [decision-rules.md](decision-rules.md) の二分岐（会話由来は [save.md](save.md)、ソース原本があれば [ingest.md](ingest.md)）に従って保存する。query 経由は通常会話起点なので、save がデフォルトとなる。

### 保存不要なケース

- 既存ページの組み合わせのみで答えが出る
- 個別具体的すぎて再利用性が低い（特定の場面でしか使わない計算結果など）
- 既存ページへの軽微な追記で済む

軽微な追記で済む場合は対象ページに直接 `Edit` で追記し、`updated` を today に。

## ステップ7: 完了レポート

- 参照したページ数とパス
- 統合回答（マークダウン本文）
- 検索経路: `index ファースト経路で完結` / `ステップ1.5 を経由` / `Grep フォールバックを使った` のいずれか
  - フォールバックを使った場合: 該当ジャンル名と、index/overview のどこに不足があったかを併記
- 保存判断の結果（新規作成 / 既存追記 / 保存なし）
- もし矛盾を検出したら lint へ回す候補として記録

## ステップ8: 操作ログ追記

検索終了時、参照したページが属するジャンルの `log.md` に追記する。**保存判断の結果（save / no-save）に関わらず必ず記録する**。

これは `curiosity` 動詞のサンプリング除外集合として機能させるためで、手動 query で活性化したページを次回 curiosity サイクルで重複して点検しないようにする目的を持つ。

### 追記形式

```markdown
## YYYY-MM-DD

- query: <質問の要約（30文字程度）>
  - 参照: [[ページX]], [[ページY]], [[ページZ]]
  - 結果: <no-save / save-rejected / saved as [[新ページ]] / appended to [[既存ページ]]>
```

複数ジャンルにまたがる参照があった場合は、**参照ページが属する全ジャンルの `log.md` に同じエントリを追記** する（除外集合の取りこぼしを防ぐため）。

### 記録粒度

- 質問の要約は 30 文字程度。長い質問は要点だけを抜き出す
- 参照ページは Read した全ページを列挙（メタファイル `_overview.md` / `index.md` は含めない）
- 結果は 4 種類のいずれか（「実際に何が起きたか」を表す形に揃える）:
  - `no-save`: 保存判断で「保存不要」と判定した場合
  - `save-rejected`: 保存判断で「保存すべき」と判定したが、ユーザーが拒否した場合
  - `saved as [[新ページ]]`: 新規ページとして保存した場合
  - `appended to [[既存ページ]]`: 既存ページに追記した場合

## 検索のコツ

- `_overview.md` は必ず読む。知識マップと横断テーマが質問の位置付けを示してくれるため、探索効率を大きく左右する
- `type: synthesis` ページは横断知識の集約点。比較・全体像の質問では真っ先に当たる
- wikilink は LLM の判断で取捨選択する。機械的に全 hop を辿らず、関連性が薄いリンクは追わない
- Grep フォールバックの多用は index/overview の品質低下を示すシグナル。lint で改善候補を確認する
